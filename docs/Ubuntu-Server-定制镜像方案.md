# Ubuntu Server 定制镜像与整盘安装方案

文档版本：V0.2  
编写日期：2026-11-07  
状态：已落地构建脚本、手动 workflow 与安装器；尚未在 Linux 服务器完成镜像构建与实机验证。实际运行步骤见 [构建与运行](构建与运行.md)。

## 1. 需求与交付目标

经常使用 Ubuntu Server 重装服务器，每次安装官方系统后，都需要重复安装系统工具、开发依赖、Docker，卸载不需要的软件并调整配置。

本项目将公共初始化工作提前到镜像构建阶段，交付一份可以制作成启动 U 盘的 ISO。安装器把已经初始化完成的 Ubuntu 系统写入目标硬盘，安装完成后的第一次启动即可使用。

### 1.1 已明确的要求

1. 使用 **Alpine Live Installer + Ubuntu Server 预制系统镜像 + safe whole-disk write installer** 的组合。
2. 硬盘中最终运行的是完整 Ubuntu Server；Alpine 仅作为安装环境。
3. 系统环境、开发依赖、Docker 及公共配置在构建镜像时准备完成。
4. Ubuntu 系统中彻底移除自带的 Snap，不保留 snapd 或预装 Snap 应用。
5. 不使用首次开机初始化脚本完成软件安装或系统定制。
6. 选盘界面默认倒计时 **30 秒**。
7. 用户未作选择时，默认选择容量最大的一块合格硬盘。
8. Ubuntu APT 软件源与 Docker 的 APT 安装仓库均使用国内镜像源，并保留在安装后的系统中。
9. 不配置 Docker Hub 等容器镜像加速服务，不写入 Docker 的 `registry-mirrors`。
10. 镜像预设首个普通用户 `ubuntu`，UID 固定为 `1000`，同时预设用户已经指定的初始密码；安装期间不询问账号密码。初始密码已保存到本地不入库配置，实际值不写入方案或日志。
11. 安装成功进入系统后，由用户手动修改密码，不强制首次登录改密。
12. 沿用 Ubuntu Server 的普通用户 + sudo 管理方式，root 账号保持锁定，不设置 root 密码，不提供 root 直接登录。
13. 目标系统确定为 **Ubuntu Server 24.04 LTS**，使用已签名的 noble APT 仓库构建，记录实际包版本和来源。
14. 仅制作 **x86_64 / amd64** 架构；安装 ISO 与目标 Ubuntu 系统均支持 **UEFI 和传统 BIOS**。
15. 目标设备是常见 PC 主机和服务器，硬盘为普通 SSD 或 HDD，无特殊硬件驱动要求。首版不适配 Secure Boot，安装和运行以关闭该功能为前提。
16. [基础工具清单](基础工具候选清单.md) 第 1 节基础集合全部纳入预装，第 2 节基础系统能力保留并验收；第 3 节可选工具不自动纳入。
17. 预装编译工具和发行版 Python，包含 venv、pip、开发头文件及 uv；pip 默认使用国内源。Node.js、Java、Go、Rust，以及数据库与 Web 服务均不纳入预装，详见 [开发环境预装清单](开发环境预装清单.md)。
18. 容器环境预装 Docker Engine、CLI、containerd、Buildx 和 Compose 插件，使用构建时国内 Docker APT 仓库中适配 Ubuntu 24.04 amd64 的最新稳定版本组合。
19. 待确认清单原第 3 节的建议配置已采用。确定采用阿里云 Ubuntu / Docker APT 源、清华 pip / uv 源、SSH 22 端口密码登录、DHCP、自动生成主机名、2 GiB 交换文件、sudo 管理 Docker，以及安装完成后手动重启。
20. 保留系统后台更新检查，关闭 SSH 登录欢迎信息和更新提示，关闭自动安装及自动重启，由用户手动维护系统补丁。
21. ISO 和磁盘镜像大文件保存在构建服务器，不上传 GitHub；GitHub 仅保存脱敏日志、软件清单、校验和及测试报告等小文件。
22. 最终安装与使用验收由用户自行完成，采用虚拟机和实体机器 U 盘安装两种方式。构建流程保留必要的自动检查，生成待用户验收的 ISO，不把尚未执行的完整安装测试标记为通过。
23. 首版采用混合 ISO 直接整盘写入 U 盘的安装方式，并支持虚拟机直接挂载 ISO；暂不适配或验收 Ventoy。
24. 首版不制定最小设备规格，不开展低内存或小容量设备专项适配；保留目标盘容量、扇区兼容性和镜像完整性等安装必要检查。
25. 选盘后等待一次明确清盘确认，确认步骤不设置自动倒计时；未确认前不清盘、不写入目标硬盘。

### 1.2 本文采用的默认设计

以下汇总已确认要求与当前设计。系统产品配置已经全部确定，剩余构建接入事项见第 16 节：

| 项目 | 当前配置 |
|---|---|
| 目标系统 | Ubuntu Server 24.04 LTS，具体点版本和来源摘要随构建锁定 |
| 目标架构 | x86_64 / amd64 |
| 启动方式 | UEFI 与传统 BIOS 均支持，覆盖安装介质及目标系统 |
| 目标磁盘 | 普通本地 SATA / NVMe SSD 或 HDD；特殊控制器不在首版适配范围 |
| 分区方式 | GPT + BIOS Boot 分区 + EFI 系统分区 + ext4 根分区 |
| 系统交换空间 | 2 GiB 交换文件，不单独建立交换分区 |
| 安装网络 | 完全离线；基本系统与 Docker 无需安装时下载 |
| Ubuntu APT 源 | 阿里云国内镜像，地址保存在构建配置中 |
| Docker APT 安装源 | 阿里云国内 docker-ce 镜像仓库，地址保存在构建配置中 |
| pip / uv 包源 | 清华 PyPI 镜像 |
| Docker 镜像加速 | 不配置 |
| 登录账号 | 首个普通用户 `ubuntu`，UID 为 `1000`，具有 sudo 权限 |
| root 策略 | 保持锁定，不设置密码，禁止本地及 SSH 直接登录 |
| 初始密码 | 使用已指定的值，由本地不入库配置提供；进入系统后手动修改 |
| 账号交互 | 安装时不询问用户名、密码或 SSH 公钥 |
| 网络配置 | 通用以太网 DHCP，默认不询问网络参数 |
| 主机名 | 安装时自动生成 `ubuntu-<机器标识短串>` |
| SSH | 启用，22 端口，允许 `ubuntu` 密码登录，禁止 root 登录 |
| 时区与语言 | Asia/Shanghai；默认 en_US.UTF-8，预留中文 locale |
| 系统更新 | 保留后台更新检查，关闭 SSH 登录提示，关闭自动安装及自动重启，手动维护；见第 6.1 节 |
| 安装结束 | 提示拔出 U 盘，由用户手动重启 |
| 清盘确认 | 30 秒超时只确定目标硬盘；开始写盘前仍需明确确认 |
| Secure Boot | 首版不支持，采用关闭 Secure Boot 的安装和运行配置 |

“选中最大硬盘”与“开始清空并写盘”是两个步骤。30 秒无操作后选中最大合格硬盘，再等待一次明确清盘确认；未确认前不进行破坏性操作，不自动进入整盘覆盖。

## 2. 总体架构

```text
Ubuntu 官方签名的 noble APT 软件包（通过国内镜像下载）
            │
            ▼
文件型 raw 磁盘：debootstrap + chroot 安装基础系统
            │
            ▼
执行版本化定制脚本
  ├─ 安装系统工具与开发依赖
  ├─ 安装 Docker Engine 与 Compose
  ├─ 移除 Snap 与其他指定软件
  ├─ 应用公共系统配置
  └─ 清理母机身份、凭证与临时状态
            │
            ▼
卸载文件系统、释放 loop → 压缩完整磁盘为 ubuntu.img.zst
            │
            ▼
打包 Alpine Live ISO
  ├─ Alpine 内核、启动文件与运行环境
  ├─ 交互式安装器
  ├─ ubuntu.img.zst
  ├─ 校验和与版本清单
  └─ 安装说明
            │
            ▼
U 盘启动 → 选盘 → 确认清盘 → 写入 → 自动扩容与单机收尾
            │
            ▼
第一次从硬盘启动：直接进入已初始化完成的 Ubuntu
```

核心交付对象是完整磁盘镜像，其中已经包含分区表、文件系统、内核、引导程序、软件和配置。安装器采用整盘覆盖方式部署镜像，不保留目标盘上的原分区和数据。

## 3. 工作在什么阶段完成

| 工作 | 构建阶段 | Alpine 安装阶段 | Ubuntu 首次启动 |
|---|---|---|---|
| 安装系统与开发软件 | 完成 | 无需下载或安装 | 已可使用 |
| 安装 Docker 与 Compose | 完成 | 写入现有镜像内容 | 正常启动 Docker 服务 |
| 移除 Snap | 完成并验证 | 无需执行 | 系统中不存在 Snap |
| 公共系统配置 | 完成 | 按需覆盖参数 | 正常生效 |
| 硬盘分区与数据部署 | 生成模板布局 | 写盘并扩容 | 已完成 |
| 用户与认证信息 | 创建 `ubuntu` 及预设密码、sudo 权限 | 沿用镜像预设，不询问或重设密码 | 直接登录，用户自行改密 |
| 主机名 | 准备命名规则 | 自动生成 `ubuntu-<机器标识短串>` | 正常生效 |
| machine-id 与 SSH 主机密钥 | 清除母机值 | 为目标机器生成 | 使用独立身份 |
| 网络配置 | 准备通用模板 | 写入 DHCP 或静态配置 | 正常启动网络服务 |
| 初始化业务脚本 | 不建立首次启动任务 | 完成所有安装收尾 | 不执行定制初始化 |

Ubuntu 首次启动允许执行 systemd、网络、SSH、Docker 等服务本身的正常启动过程。首次启动前必须完成软件安装、依赖解析、身份生成、扩容和配置写入。

## 4. Ubuntu 母镜像构建

### 4.1 基础系统来源

当前实现采用 `debootstrap + chroot`，直接在新建的文件型 raw 磁盘内安装 Ubuntu 24.04，避免构建阶段的安装器交互和对 KVM 的依赖。不使用终端用户首次开机脚本，也不依赖 cloud-init。

Ubuntu Server 22.04 / 24.04 x86_64 可以作为宿主，支持实体机或 VMware 虚拟机。当前直接使用根目录 `build.sh` 命令行构建，不需要 GitHub Runner；workflow 暂缓接入，保留仅手动触发的配置。实际步骤见 [构建与运行](构建与运行.md)。

- `debootstrap` 使用 Ubuntu archive keyring 验证 noble 仓库，所有 Ubuntu 包来自配置的国内源。
- 安装 `ubuntu-minimal`、`ubuntu-standard`、内核、固件及显式服务器软件集合；`ubuntu-server-minimal` 强制依赖 snapd，因此不采用该元包。
- 直接创建 `ubuntu` 为首个普通用户，校验 UID/GID 均为 `1000`。
- 在私有挂载命名空间内操作新建 raw 对应的 loop 设备，退出时卸载并释放；不接受宿主物理盘作为构建目标。
- 定制完成后校验账号、软件与配置，清理身份，卸载文件系统后压缩完整 raw。
- 记录 Ubuntu 包版本、仓库、脚本摘要以及 uv、Alpine 输入摘要。在线仓库仍会更新，严格复现需要另外保留仓库快照。

### 4.2 定制内容

以配置文件和版本化脚本维护公共环境，避免手工修改母机后无法重建。

| 分类 | 规划内容 |
|---|---|
| 系统工具 | 已确认完整的网络、端口、DNS、抓包、带宽、TLS、防火墙、进程、磁盘及文件运维工具基础集合，详见 [基础工具清单](基础工具候选清单.md) |
| 开发环境 | 编译工具 + 发行版 Python / venv / pip / 开发头文件 + uv；pip 使用国内源，详见 [开发环境预装清单](开发环境预装清单.md) |
| 容器环境 | Docker Engine、CLI、containerd、Buildx、Compose 插件，采用构建时国内 Docker APT 仓库的最新稳定版本组合 |
| 软件清理 | snapd、Snap 应用，以及用户明确指定的其他软件 |
| 跨网络访问 | Tailscale 客户端与守护进程，开机自启；安装后用户手动认证 |
| 公共配置 | 时区、locale、软件源、日志轮转及明确需要的系统参数 |
| 可选资源 | 预置容器镜像、业务程序、离线维护包 |

基础运维工具和开发环境范围已确认。编译工具、发行版 Python 与 uv 纳入预装，Node.js、Java、Go、Rust，以及数据库与 Web 服务不纳入预装；具体包版本在构建时锁定。

定制脚本应支持重复执行，失败时停止构建并记录日志。构建结束导出包名、版本、来源和配置摘要。

### 4.3 国内 APT 软件源

在母镜像安装阶段指定国内 Ubuntu 镜像源，并在安装后核对最终 APT 配置；执行系统更新和软件安装前完成配置。最终系统保留这些源，后续手工使用 APT 时直接从国内镜像获取软件。

已采用的镜像站配置：

| 用途 | 镜像地址 | 构建配置项 |
|---|---|---|
| Ubuntu 系统软件包 | `https://mirrors.aliyun.com/ubuntu/` | `ubuntu_apt_mirror` |
| Docker APT 软件包 | `https://mirrors.aliyun.com/docker-ce/linux/ubuntu` | `docker_apt_mirror` |

具体镜像站可以替换，构建时验证其支持目标 Ubuntu 发行代号、amd64 架构和所选软件版本。配置规则如下：

- 兼容 Ubuntu 24.04 默认的 deb822 文件 `/etc/apt/sources.list.d/ubuntu.sources`；同时检查传统 `sources.list` 及其他条目，避免重复启用官方海外源。
- Ubuntu 镜像保留对应发行版的基础、updates、security 和 backports 套件，不因换源漏掉安全更新；保留需要的软件组件。
- Docker 使用独立的 APT 源文件和 keyring，通过 `Signed-By` 绑定 Docker 仓库签名密钥；Ubuntu 软件源也保留签名验证。
- 国内镜像不可用时明确报告失败，不静默切回海外源，不关闭签名验证。
- 软件源地址、发行代号和实际包版本写入构建清单。

这里的 Docker 国内源用于下载 Docker Engine、CLI、containerd、Buildx 和 Compose 的 DEB 软件包。容器镜像拉取沿用 Docker 默认行为，不设置镜像加速地址。

## 5. Snap 移除方案

Snap 清理在母镜像构建阶段完成，流程为：

1. 检查 snapd 和已安装 Snap 的实际状态。
2. 按依赖顺序移除 Snap 应用，包括存在时的 LXD、snap-store、基础 core 包及 snapd Snap。
3. 停止 Snap 相关服务与 socket，卸载现有 Snap 挂载。
4. 使用 APT 清除 snapd 软件包及其系统配置。
5. 清理 Snap 缓存、残留目录和母机用户目录中的 Snap 数据。
6. 设置 APT 策略，阻止 snapd 被常规依赖操作重新安装。
7. 检查后续软件清单，避免使用会转装 Snap 的过渡包。

建议的 APT 策略文件：

```text
# /etc/apt/preferences.d/no-snap.pref
Package: snapd
Pin: version *
Pin-Priority: -1
```

该规则阻止 APT 按常规候选版本安装 snapd；它是包管理默认策略，不用于阻止管理员主动改变系统。

构建验收必须确认：

- snapd 未处于已安装状态，且不残留需要清除的包配置。
- snap 命令不存在，Snap 相关服务和 socket 不处于启用状态。
- 不存在 Snap 挂载、应用数据或包含母机身份的残留。
- APT 解析最终软件清单时不会重新引入 snapd。

## 6. Docker 与开发环境

Docker 在构建阶段通过第 4.3 节中的国内 Docker APT 仓库 `stable` 通道安装。每次新构建刷新 APT 索引，选择适配 Ubuntu 24.04 amd64、满足相互依赖的最新稳定版本组合，不使用 test、nightly 或预发布通道。安装包为 `docker-ce`、`docker-ce-cli`、`containerd.io`、`docker-buildx-plugin` 和 `docker-compose-plugin`。

“最新版”指该国内仓库在构建时实际提供的最新稳定版，不承诺镜像站与上游实时同步。解析后将精确包版本和来源写入本次构建清单；之后的新构建重新解析最新稳定版本，既有 ISO 内的软件不会在安装时临时下载或升级。

配置服务随系统正常启动，并预先验证 Engine、Buildx 与 Compose 可用。安装后的系统保留此国内 APT 仓库，便于后续维护和升级。

公共配置包括日志轮转和存储位置。不配置 Docker 镜像加速地址，也不为此写入 `registry-mirrors`；其他需要的 `daemon.json` 配置正常保留。代理、私有仓库账号和 TLS 凭证不得作为公共默认值写入母镜像。

正式镜像不预装业务容器镜像或业务数据。离线验收用容器仅放入测试镜像，验证完成后不保留在正式母镜像中；构建时的容器、业务卷、登录凭证和测试数据均需清理。

`ubuntu` 通过 sudo 管理 Docker，不加入 docker 组；Docker 数据目录为 `/var/lib/docker`，配置日志轮转。

Python 使用 Ubuntu 发行版维护的解释器，安装编译工具、venv、pip 与开发头文件。uv / uvx 采用构建时下载并验证的预编译二进制，不引入 Rust 工具链。pip 配置系统级国内源，uv 单独配置相同国内索引并默认使用系统 Python；详细规则和验收要求见 [开发环境预装清单](开发环境预装清单.md)。

### 6.1 系统更新策略（已确认）

保留联网时的后台软件索引刷新，关闭 SSH 登录时的更新与重启提示，关闭无人值守安装及自动重启。系统安全补丁、功能修复和需要的重启由用户在维护窗口手动执行。

构建阶段写入明确的 APT 配置并检查最终生效值，建议配置如下：

```text
APT::Periodic::Enable "1";
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Download-Upgradeable-Packages "0";
APT::Periodic::Unattended-Upgrade "0";
Unattended-Upgrade::Automatic-Reboot "false";
```

实现规则：

- 保留 `apt-daily.timer` 等软件索引刷新能力，关闭 `apt-daily-upgrade.timer` 等自动升级入口；核对实际基础系统是否还有其他自动安装任务。
- SSH 登录不展示可用更新数量或需要重启等提示；不为登录提示额外安装 `update-notifier-common`。用户可用 `apt list --upgradable` 和检查 `/var/run/reboot-required` 手动了解状态。
- 不为系统或 Docker 增加自动升级任务，不自动安装安全更新，也不自动下载待升级软件包；刷新索引和提示数据仍需少量网络访问。
- 用户主动执行 APT 更新、安装、升级和重启不受限制；保留 APT 安全更新源。
- 离线时不阻塞登录、服务启动或安装流程；更新检查恢复联网后继续进行，手动查询结果以最近成功刷新为准。
- 这些设置在构建阶段完成，不通过首次启动初始化脚本下发。

验收时检查 APT 配置最终值和定时器状态，确认联网检查不会自动安装软件或重启，SSH 登录不显示更新提示，手动 APT 操作仍然可用。系统中的补丁维护由用户负责，仅重建安装 ISO 不会更新已部署机器。

### 6.2 Tailscale（已确认）

在母镜像构建阶段预装 `tailscale` 与 `tailscaled`，启用 `tailscaled.service`，首次进入系统时软件和服务已经就绪。Tailscale 的设备认证由用户安装后手动完成，不作为系统初始化或安装成功的前置条件。

- 构建时通过经过签名验证的软件源安装稳定版，记录实际版本与来源；Ubuntu 和 Docker 继续沿用第 4.3 节已确定的国内源。
- 构建和安装过程不执行 `tailscale up`，不请求或写入 Auth key、OAuth 凭证及其他注册密钥，不增加自动注册服务或首次开机脚本。
- 导出母镜像前停止 `tailscaled`，清除 `/var/lib/tailscale/` 中的状态、设备私钥及构建缓存，保留服务启用配置；检查镜像没有预注册设备身份。
- 服务正常启动时可以生成本机所需的运行状态；每台机器由用户独立认证，不能复制构建虚拟机的 Tailscale 状态。
- 不预设子网路由、出口节点或 Tailscale SSH；常规 SSH 沿用 OpenSSH 配置。用户认证后按需自行配置 Tailscale 功能。
- 不启用 Tailscale 自身的自动更新功能，后续软件更新由用户手动维护。
- 未认证或断网时，安装、登录和本地服务仍正常可用；Tailscale 跨网络连接需要联网并完成认证。

安装后在目标机器执行：

```bash
sudo tailscale up
# 打开命令显示的认证链接，登录自己的 Tailscale 账号并授权
tailscale status
tailscale ip -4
```

认证后的状态仅保存在该目标机器，后续重启由 `tailscaled` 自动恢复连接；需要重新认证时遵循所属网络的设备审批、密钥有效期和访问策略。构建清理逻辑不得在已安装系统每次开机时执行，以免删除用户完成的认证。

### 6.3 SSH 登录显示（已确认）

SSH 登录成功后直接进入命令行，不显示 Ubuntu 欢迎信息、文档链接、系统资源与 IP 概览、Ubuntu Pro / ESM 宣传、更新数量、重启提醒和上次登录信息。

配置在母镜像构建时完成：

- 设置 SSH 服务端有效配置 `PrintMotd no`、`PrintLastLog no` 和 `Banner none`，通过 `sshd -t` 与 `sshd -T` 检查语法和最终生效值，避免其他配置片段覆盖。
- Ubuntu 通过 PAM 也会显示 MOTD；仅禁用 `/etc/pam.d/sshd` 中调用 `pam_motd.so` 的会话条目，保留其他认证、账号和会话模块。单独设置 `PrintMotd no` 不足以关闭这些输出。
- 检查 `/etc/profile`、`/etc/profile.d/` 和 `ubuntu` 用户的 Shell 启动文件，关闭发行版或构建流程附加的欢迎输出，包括首次 sudo 使用说明；不增加替代欢迎信息。
- 保留正常的密码认证交互、认证失败及其他错误信息，登录与审计记录继续保留。
- SSH 登录显示与后台 APT 更新检查分开配置；本节不删除更新源或关闭第 6.1 节保留的索引刷新任务。

验收使用实际交互式 SSH 会话检查首次登录和后续登录的输出；确认直接出现 Shell 提示符，认证、sudo 和远程命令执行正常。

## 7. 磁盘镜像布局与兼容性

### 7.1 第一版布局

```text
GPT 磁盘
├─ BIOS Boot 分区：建议 2 MiB，不建立文件系统，供 GRUB BIOS 引导使用
├─ EFI 系统分区：FAT32，建议 512 MiB
└─ Ubuntu 根分区：ext4，占用剩余模板空间，可向后扩展
```

- 根分区放在最后，便于安装到更大硬盘后扩容。
- 默认不启用 LVM、整盘加密、RAID 或双系统保留。
- 内核和 initramfs 包含常见 SATA、NVMe、文件系统及网络驱动。
- EFI 引导需要具备可移植的 fallback 路径，不依赖构建虚拟机的 NVRAM 启动项。
- 同一目标磁盘同时具备 GRUB 的 BIOS 与 UEFI 引导能力；BIOS 使用 GPT 中的 BIOS Boot 分区，UEFI 使用 EFI 系统分区。
- 引导收尾显式处理两类 GRUB 目标及相应模块，不只根据安装 U 盘当前的启动方式安装其中一种。
- 首版不加入自定义 Secure Boot 签名、密钥登记或固件信任配置流程。Alpine 安装环境的签名与信任链需要独立维护，按用户对复杂度的取舍暂不实施。

### 7.2 镜像尺寸

当前实现模板默认 24 GiB，可在 `config/build.json` 中调整；目标盘必须容纳完整 raw 并额外预留至少 1 MiB。此项为镜像容量检查，不是最低硬件规格承诺。

最小设备配置不纳入首版规划和专项验收。镜像长度仍写入 manifest，安装器按实际镜像判断目标盘是否可安装，不因取消最低配置规划而跳过必要检查；构建服务器的资源预检也正常保留。

`ubuntu.img.zst` 的压缩大小主要影响 ISO 体积；目标盘是否可安装，以解压后的完整 raw 镜像字节数、扇区布局和安装预留需求为准，不能按压缩文件大小判断。

构建时记录逻辑扇区大小。第一版按普通家用 SSD / HDD 范围，验证 512 字节逻辑扇区及 512e 硬盘；4Kn 专门适配不纳入首版，遇到不兼容扇区格式时停止安装。SSD / HDD 描述的是介质类型，安装器仍需自动检查实际逻辑扇区大小。

## 8. Alpine Live 安装环境

Alpine 安装环境应提供：

- 内核、initramfs、UEFI 与传统 BIOS 引导文件。
- 与安装介质匹配的 USB、SATA、NVMe、文件系统及控制台驱动。
- 安装器运行环境、磁盘探测、Zstandard 解压、写盘和进度工具。
- GPT 修复、分区扩容、ext4 检查与扩容工具。
- 挂载、chroot、校验和、日志及关机工具。

实现时按所选 Alpine 版本核对具体包名、工具参数及 BusyBox 与 GNU 工具差异。

ISO 内建议使用以下结构：

```text
/installer/                 安装器与界面资源
/payload/ubuntu.img.zst      已初始化的 Ubuntu 完整磁盘镜像
/payload/manifest.json       版本、镜像长度、扇区要求、摘要和配置摘要
/payload/SHA256SUMS          介质内容校验
/licenses/                  随发行资源所需的许可证说明
```

大型镜像可能超过 FAT32 的单文件限制，因此不要求用户把 ISO 内容直接解压到 FAT32 U 盘。首版支持将混合启动 ISO 整体写入 U 盘，验证其 UEFI、传统 BIOS 启动和大文件读取能力。

实体机器使用 Rufus 的 DD 镜像模式、balenaEtcher 或 `dd` 等工具将 ISO 直接整盘写入 U 盘；虚拟机直接将 ISO 挂载为虚拟光盘。首版不做 Ventoy 专门适配，也不将其纳入验收范围。

## 9. 选盘与 30 秒倒计时

### 9.1 合格硬盘条件

默认候选设备需要同时满足：

- 是可写的整块物理硬盘，而非分区、loop、光驱或 device-mapper 逻辑设备。
- 容量满足 raw 镜像长度及安装布局要求。
- 逻辑扇区大小与镜像兼容。
- 不属于安装介质及安装环境使用的任何底层磁盘。
- 不是只读设备，默认也不包括可移动盘和 USB 外接盘。
- 未被其他挂载、swap、LVM、RAID 或映射设备占用。

识别安装介质时，需要解析安装资源挂载来源及其父设备，识别直接写入 ISO 的 U 盘或虚拟光驱，并排除安装环境使用的底层磁盘。无法确认介质来源时，停止自动选盘并要求人工处理；不为未支持的启动方式回退到直接选择最大盘。

### 9.2 界面与计时规则

进入选盘界面前完成候选设备扫描，再开始 30 秒倒计时。显示设备路径、型号、序列号、容量和总线类型，并突出显示当前默认盘。

```text
请选择 Ubuntu 安装硬盘

  1. /dev/sda       SATA SSD     480 GB    序列号：...
  2. /dev/nvme0n1   NVMe SSD       1 TB    序列号：...  [默认]

30 秒内未选择，将选中容量最大的合格硬盘。
剩余时间：30 秒

选择编号并回车；直接回车接受默认盘；按取消键退出。
```

规则如下：

1. 默认盘为合格候选中按实际字节数排序最大的硬盘。
2. 容量相同时按序列号、稳定设备标识排序；界面展示实际选中的设备。
3. 用户开始输入或操作选择后，取消自动倒计时，进入人工选择状态。
4. 直接回车接受默认值；30 秒完全没有操作时自动选中默认盘。
5. 只有一块合格硬盘时，仍显示完整倒计时和设备信息。
6. 没有合格硬盘时不启动倒计时，不降级选择安装 U 盘。
7. 进入写盘前重新检查设备身份、容量、只读标志、占用状态及介质排除结果。

### 9.3 清盘确认

选盘完成后显示目标盘的型号、序列号、容量和“整盘数据将被清空”的提示，输入 `y` 后回车确认（也接受大写 `Y`）。直接回车或其他输入取消安装，不写盘。此步骤不设置自动确认倒计时。

设备路径不是唯一身份依据。需要在选盘时保存稳定标识，并在写盘前核对；发现设备更换、消失或身份不一致时终止安装。

## 10. 安装与收尾流程

| 阶段 | 操作与完成条件 |
|---|---|
| 介质检查 | 校验 manifest、压缩镜像摘要与压缩流完整性 |
| 设备选择 | 完成候选过滤、30 秒选盘与目标身份锁定 |
| 默认配置 | 自动使用镜像预设的 `ubuntu` 账号和初始密码；主机名和网络使用默认配置，按需覆盖，不作为默认必填步骤 |
| 清盘确认 | 展示最终目标和影响范围，用户明确确认 |
| 镜像写入 | 流式解压并整盘写入，显示进度，检查解压与写入退出状态 |
| 写入验证 | 刷新并回读校验镜像覆盖范围；完整验证安排在扩容和修改配置之前 |
| 布局处理 | 刷新分区表、将 GPT 备份移至实际盘尾、扩展最后的根分区 |
| 文件系统扩容 | 在未挂载状态下检查并扩展 ext4，确认可用空间 |
| 目标配置 | 挂载目标系统，写入身份、认证、网络及安装记录 |
| 引导收尾 | 更新磁盘标识引用，生成 initramfs 与 GRUB 配置，同时安装 BIOS GRUB 和可移植 EFI 引导 |
| 完成检查 | 核对服务启用状态、Snap 移除结果、关键文件与挂载配置 |
| 安全退出 | 同步、卸载目标文件系统，提示拔出 U 盘并重启 |

压缩镜像采用流式写入，避免要求内存容纳整个解压镜像。实现必须正确传播管道各阶段的失败状态；解压或写盘任一失败，都不能继续显示安装成功。

整盘写入不是原子操作。断电或写入失败后，目标盘可能处于不完整状态，恢复方式是从安装介质重新安装；写入开始后不能提供保留旧系统的回滚承诺。

## 11. 预设账号与机器独立身份

### 11.1 镜像预设账号密码

构建镜像时，按 Ubuntu Server 常规安装方式创建首个普通用户，随系统镜像一并交付：

| 项目 | 规则 |
|---|---|
| 用户名 | `ubuntu` |
| 用户 UID | 固定为 `1000`，作为系统首个普通用户 |
| 主用户组 | `ubuntu`，GID 为 `1000` |
| 家目录与 Shell | `/home/ubuntu`，默认 `/bin/bash`，目录和文件属主与 UID/GID 一致 |
| 初始密码 | 统一预设，用户已指定，保存在本地不入库的 `config/local.env` 中 |
| 管理权限 | 加入 sudo 组，执行 sudo 时正常验证密码 |
| root 账号 | 保留系统必需的 UID 0 账号，密码保持锁定，不设置 root 密码，不提供本地直接登录 |
| SSH root 登录 | 禁止，最终有效配置为 `PermitRootLogin no` |
| 安装时交互 | 不弹出用户名、密码、确认密码或 SSH 公钥输入步骤 |
| 首次登录 | 可以直接登录，不设置密码过期或强制改密流程 |
| 后续改密 | 用户进入系统后执行 `passwd` 自行修改 |

安装器沿用镜像中的账号和密码哈希，不在安装时生成随机密码，也不在安装或后续开机时重置用户密码。同一镜像安装的机器在用户改密前使用相同初始凭据。

日常登录和操作均使用 `ubuntu`，管理命令通过 `sudo` 提权，不引导用户设置或使用 root 登录凭据。root 系统账号本身仍然存在，用于系统服务和特权操作。

构建时检查 `id -u ubuntu` 为 `1000`、主组 GID 为 `1000`，且不存在其他普通用户占用这些标识。镜像复制和安装收尾保留数字 UID/GID 与文件属主，不重新分配账号标识；发现不符时构建或安装验收失败，不静默接受其他 UID。

预设账号是明确保留的交付账号，与需要清理的临时构建账号分开处理。初始密码不写入 Git、公共配置、构建清单或日志；目标系统通过 `/etc/shadow` 保存密码哈希。构建和安装所需的临时构建账号、其他凭证及个人数据仍需清理。

### 11.2 安装阶段生成机器独立身份

母镜像清理 machine-id、SSH 主机密钥、构建网络绑定、DHCP 租约、随机种子和构建凭证。安装器在最终启动前完成：

1. 生成独立 machine-id，并正确处理 `/var/lib/dbus/machine-id` 的引用。
2. 在目标 Ubuntu 环境中生成 SSH 主机密钥。
3. 检查镜像预设的 `ubuntu` 账号 UID/GID 均为 `1000`，密码哈希、文件属主和 sudo 策略完整；root 保持锁定且禁止 SSH 直接登录。不覆盖预设认证信息，不要求用户输入。
4. 写入主机名、hosts 与网络配置。
5. 为目标盘生成独立 GPT 磁盘及分区标识，并按设计更新文件系统 UUID。
6. 同步更新 fstab、GRUB 及 initramfs 中的相关引用，并重新验证引导。
7. 按配置创建交换文件，记录安装版本与时间。

标识更新与引导重建必须作为完整步骤验证，不能只修改 UUID 而保留指向旧标识的启动配置。

Alpine 可通过挂载目标系统并 chroot 执行 Ubuntu 自身的工具。需要的工具提前存在于母镜像中，安装期间不联网安装依赖；chroot 不启动业务服务。

最终系统使用独立的 Netplan 配置。cloud-init 默认移除或禁用，并清除母机状态；具体处理方式需在所选 Ubuntu 基础系统上验证，确保网络和登录均不依赖 cloud-init 首次启动配置。

## 12. 配置与构建产物

建议分开维护公共构建配置、安装默认值和每次安装输入：

| 配置 | 典型内容 | 保存位置 |
|---|---|---|
| 公共构建配置 | Ubuntu 版本、Ubuntu 与 Docker 国内 APT 源、软件集合、Docker 版本、移除列表、公共参数 | 项目版本管理 |
| 安装默认值 | 30 秒倒计时、最大盘策略、`ubuntu` 用户名、默认时区和网络模式 | ISO 中的默认配置 |
| 构建机密配置 | 预设初始密码或其哈希 | 本地不入库的构建配置；镜像内仅保存所需密码哈希 |
| 可选单机覆盖 | 主机名、静态 IP 等 | 按需提供，默认不要求人工输入 |

交付镜像保留明确要求的 `ubuntu` 预设账号及统一初始密码的哈希。密码不以明文写入公共配置、构建清单或安装日志；其他临时母机账号及凭证不保留。用户安装后修改密码，后续重启不得恢复为预设值。

每次构建输出：

- 可启动安装 ISO 及 SHA256。
- Ubuntu 压缩磁盘镜像、解压长度与摘要。
- 构建 manifest，包含基础介质摘要、架构、扇区要求、脚本版本和配置摘要。
- 已安装软件包与版本清单。
- 构建日志、测试报告及交付说明。

完整 ISO 默认保存至构建服务器的 `/srv/ubuntu-customizer/releases/<build-id>/`，不依赖 Runner 临时工作目录。GitHub Artifact 仅上传脱敏日志、清单、SHA256 与测试报告，不上传 ISO、磁盘镜像或包含这些文件的归档；用户通过 SFTP / SCP 获取本地 ISO。详细上传范围见 [构建与 GitHub Actions 方案](构建与GitHub-Actions方案.md)。

版本清单用于追溯实际输入。若需要严格重建相同软件集合，还需冻结软件源快照或保存具体安装包，不能只依赖持续更新的在线仓库。

```text
├─ tests/                   选盘、写入、凭证与 workflow 安全测试
└─ reports/                 忽略入库，仅暂存固定的小文件报告
```

完整产物与工作文件保存在 `/srv/ubuntu-customizer/`，不放进仓库。代码已实现；Linux 完整构建与硬件验证仍待执行。

## 14. 检查与验收标准

构建阶段负责软件、配置、镜像完整性与引导文件等自动检查，输出 ISO、SHA256、检查结果和以下验收清单。用户自行执行虚拟机及实体机器 U 盘安装测试，并确认最终使用结果。

首版不要求 workflow 完成自动化的 BIOS / UEFI 全量安装验收后才能提供 ISO。当前自动检查包含软件配置、压缩流、ISO 读取和双模式引导目录，尚未运行系统服务及自动启动测试。构建成功不代表人工验收通过；用户自行安排虚拟机和实体机验收。

### 14.1 构建与系统验收

- 构建流程能从锁定的输入自动生成镜像，失败时停止并保留日志。
- 压缩镜像前根分区、ESP 和临时挂载均已卸载，loop 设备已经释放。
- 已安装软件、Docker 和 Compose 版本与构建清单一致。
- Docker 容器组件来自国内 APT 仓库的 stable 通道，版本与本次构建解析的最新兼容稳定组合一致，Engine、Buildx 和 Compose 均可用。
- 基础工具清单中的已确认包和基础系统命令可用；不自动纳入可选工具，也不因安装诊断工具改变网络、防火墙或启用额外采集服务。
- 编译工具、发行版 Python、venv、pip 和 uv / uvx 在首次启动前安装完成，Python 包源配置生效；不主动安装已经排除的语言环境或数据库与 Web 服务。
- Ubuntu 与 Docker 的 APT 安装源均指向配置的国内镜像，签名验证正常，未重复启用对应海外源。
- 国内 APT 源在安装后的系统中保留，Docker 配置中没有 `registry-mirrors`。
- 系统保留后台更新检查，自动安装及自动重启关闭；有效 APT 配置与定时器状态符合第 6.1 节，SSH 登录显示符合第 6.3 节。
- 完整 ISO 保存在服务器持久目录，GitHub 上传清单中不包含 ISO 或磁盘镜像；日志和报告不泄露构建凭据。
- Snap 包、服务、应用、挂载和残留清理结果符合第 5 节要求。
- Tailscale 已安装，实际版本与来源进入清单，`tailscaled.service` 已启用；交付母镜像不含注册凭证、设备私钥或认证状态，不启用自动注册和自身自动更新。
- 镜像保留 `ubuntu` 交付账号及预设密码哈希，不保留临时构建凭证、个人用户数据和不必要的 Docker 运行状态。
- `ubuntu` 是首个普通用户，UID/GID 均为 `1000`，家目录和文件属主正确；root 密码锁定，SSH 的有效配置禁止 root 登录。

### 14.2 安装器验收（用户执行）

- ISO 可作为整盘写入的 U 盘介质启动，安装过程断网仍可完成。
- 安装 ISO 在 Secure Boot 关闭的 UEFI 和传统 BIOS 环境中分别通过启动与完整安装验收。
- 默认安装流程不要求输入用户名、密码、SSH 公钥、主机名或网络参数。
- 选盘倒计时为 30 秒，超时选中容量最大的合格盘。
- 人工选择生效，输入或选择过程中不会被倒计时切换目标。
- 正确排除安装 U 盘、只读盘、容量不足和被占用的设备。
- 无候选、相同容量、多硬盘、设备热拔插等情况有确定行为。
- 清盘确认前没有对候选目标执行破坏性操作。
- 解压失败、写入失败、回读不符或收尾失败时不报告成功。
- 大盘安装后 GPT、根分区与 ext4 扩容正确。

### 14.3 首次启动验收（用户执行）

- 拔出安装 U 盘后，目标磁盘分别通过 UEFI 与传统 BIOS 独立启动验收；UEFI 验收关闭 Secure Boot。
- 第一次启动不联网下载依赖，也不执行定制初始化脚本。
- 登录、网络、SSH、开发工具、Docker 与 Compose 直接可用。
- SSH 首次及后续登录成功后直接显示 Shell 提示符，无 MOTD、广告、系统状态、更新与重启提醒或上次登录信息。
- `tailscaled` 开机启动，未认证时不影响登录；用户联网执行 `sudo tailscale up` 后可按网络访问策略连接其他节点，重启后保留本机认证状态并恢复连接。
- 可使用 UID 为 `1000` 的 `ubuntu` 和预设初始密码登录，sudo 正常验证密码；首次登录不强制改密。
- 本地与 SSH 均不提供 root 直接登录，日常管理通过 `ubuntu` 执行 sudo。
- 用户执行 `passwd` 改密后，新密码持续生效，后续重启不恢复预设密码。
- 测试镜像中预置的验收容器能够在断网状态运行，以区分 Engine 就绪与联网拉取能力；正式镜像不保留该容器及业务数据。
- 两台独立安装的 machine-id、SSH 主机密钥和磁盘标识符合独立性要求。
- 后续重启服务行为一致，系统扩容和网络配置持续生效。

虚拟机平台由用户自行选择，可使用 QEMU/KVM、VMware、VirtualBox 等支持所需启动模式的平台。UEFI 与传统 BIOS 两种模式均按清单验证安装和硬盘启动；实体机器将 ISO 写入 U 盘后执行完整安装，检查 SATA / NVMe 存储、网卡、首次启动及重启后的使用情况。无需在开始构建前提供特定验收设备型号。

### 14.4 验收记录与反馈

- 记录构建编号、ISO SHA256、虚拟机平台或实体设备型号、启动模式及安装结果。
- 人工验收在用户实际反馈前保持“待验收”，不由 workflow 自动填为通过。
- 用户发现问题时，记录失败阶段和现象，并保留安装日志；后续结合对应构建记录定位和修复。
- GitHub 仅保存实际执行的自动检查结果及已收到的人工验收记录，不上传 ISO；用户尚未反馈的测试项目明确标记为未执行或待验收。

## 15. 分阶段实施

### 阶段一：打通最小安装链路

构建最小 Ubuntu 母镜像，移除 Snap，安装 Docker 和基础工具；生成支持 UEFI 与传统 BIOS 的 Alpine ISO，实现候选过滤、30 秒选盘、清盘确认、写盘、扩容和身份收尾；完成构建自动检查后提供待验收 ISO，由用户执行虚拟机和实体机器 U 盘安装测试，并按结果修复问题。

### 阶段二：完善个人初始化环境

落实已经确认的编译工具、发行版 Python / pip / uv 及国内包源配置，完善公共配置、软件版本锁定、详细日志、按需预置的容器镜像与常见失败处理。正式交付前这些已确认环境必须完成构建和验收。

### 阶段三：扩大硬件与部署兼容性

按实际需要支持更多网卡与控制器、4Kn、静态网络界面、加密或其他分区布局。传统 BIOS 已纳入首版；Secure Boot 当前不支持，仅在未来明确需要时单独设计与验收。
