# 构建与运行

当前采用 Ubuntu 构建机器直接执行命令行的方式，不通过 GitHub Runner。已实现统一入口 `build.sh`、母镜像构建、Alpine Live 打包和整盘安装器；GitHub workflow 保留但暂缓接入。本地检查包括 Python 安全测试、ShellCheck 和脚本语法检查。用户已在 Linux 构建机生成 ISO，并在虚拟机中完成 Live 启动、镜像写入及回读；安装收尾曾因缺少 `sgdisk` 中止，修复后的新 ISO 尚待复测，双启动模式完整安装及实体机验收尚未完成。

## 1. 构建方式与目录

使用可联网的 Ubuntu Server 22.04 / 24.04 x86_64 构建机器，也可以是 VMware 中的 Ubuntu 虚拟机。在终端运行入口即可，不需要 GitHub 账号、Runner、Actions Secret 或宿主 Docker。构建时下载软件仍需要网络访问，包括 uv 和 v2rayA 的 GitHub Releases 下载。

```text
终端 bash build.sh build → 本地构建机器
                       ├─ 创建文件型 raw 磁盘、GPT / ESP / ext4
                       ├─ debootstrap noble + chroot 完成 Ubuntu 配置
                       ├─ 校验账号、工具、软件源配置和服务启用状态
                       ├─ 安装双模式 GRUB、清理机器身份、卸载镜像
                       ├─ 压缩完整磁盘，构建 Alpine 根文件系统和 initramfs
                       └─ grub-mkrescue 生成 BIOS / UEFI 混合 ISO
```

母镜像直接从经过签名验证的 Ubuntu APT 仓库生成，不需要官方 Ubuntu 安装 ISO、autoinstall、Docker 宿主环境或 KVM。安装系统时仍使用 Alpine 离线写入完整磁盘镜像。KVM 仅在你选择 QEMU 做最终虚拟机测试时需要。

默认持久目录：

```text
/srv/ubuntu-customizer/
├─ work/<build-id>/               临时根文件系统、raw、压缩镜像、tools.log
└─ releases/<build-id>/
   ├─ ubuntu-custom-server.iso    最终 ISO，仅在打包检查成功后使用这个文件名
   ├─ SHA256SUMS                  ISO SHA256
   ├─ manifest.json               来源、包输入、镜像长度、摘要、uv / Alpine 版本
   ├─ packages.txt                Ubuntu 实际软件包版本
   ├─ package-origins.txt         Docker / Tailscale APT 候选及来源
   ├─ logs/tools.log              脱敏工具日志，仅本地保存
   └─ reports/
      ├─ build-report.json        实际检查结果，人工验收固定为 pending
      └─ build.log               阶段摘要
```

`work` 目录权限为 0700，内含带预设账号密码哈希的母镜像。完整工作目录和历史 ISO 均不自动清理，连续构建前需检查磁盘空间，按 build-id 管理已不需要的历史目录。构建目录使用 Linux 文件系统，例如虚拟机内的 ext4，不使用 VMware 共享文件夹。

## 2. 命令行直接构建（当前方式）

把项目放到 Ubuntu 构建机器上，可以 Git 检出，也可以复制完整项目目录；不要求使用 GitHub 或保留 `.git`。进入项目根目录，以下操作不依赖已有 Docker Runner。

检出仓库后，先准备本地私有密码及可选代理配置：

```bash
[ -f config/local.env ] || cp config/local.env.example config/local.env
chmod 600 config/local.env
nano config/local.env
```

填写已经约定的初始密码。`local.env` 文件本身不入库，也不随 ISO 交付；解析器接受 `UBUNTU_INITIAL_PASSWORD`、`HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`（含小写形式）和 `NTFY_URL` / `NTFY_TOPIC` / `NTFY_TOKEN`，不执行文件中的 Shell 命令，也不展开 `$变量` 或 `$(命令)`。环境变量优先于该文件。密码通过标准输入生成哈希和写入目标系统，不作为命令行参数。ntfy 三项如填写则会写入目标系统的私有配置，Token 会包含在 ISO 中。

安装构建工具：

```bash
bash build.sh setup
```

入口会在需要时调用 sudo，安装本机构建依赖并创建持久目录；该步骤会修改构建机器的软件包，通常只需执行一次。`setup` 使用宿主现有 APT 源，并读取上述代理配置；标准 Ubuntu Server 已带有启动配置解析器需要的 Python 3。Ubuntu / Docker 换源、Snap 清理、创建交付账号等操作均发生在磁盘镜像内。

检查并构建：

```bash
bash build.sh check
bash build.sh build
```

`check` 只读检查 Linux 架构、工具、内存、磁盘空间和输出路径；不需要密码配置、root 或创建目录，也不执行实际构建。mount / loop 权限和网络下载在正式构建时核对。

`build` 自动生成 UTC 时间作为 build-id，并在终端显示编号、详细日志和最终 ISO 路径。需要指定编号或配置文件时：

```bash
bash build.sh build --build-id local-001
bash build.sh build --config /absolute/path/build.json
```

已有工作目录或产物目录会拒绝复用，避免覆盖历史产物，重试时换一个编号或使用默认的自动编号。构建阶段在独立的挂载、PID、UTS、IPC 命名空间运行，并重新挂载对应的 `/proc`，使镜像内的包脚本无法通过进程枚举和常规信号操作宿主进程。入口保留宿主命名空间标识用于预检，未正确隔离时在创建构建目录前拒绝执行。入口退出会终止该 PID 命名空间内遗留的进程。

Ubuntu / Alpine 的 `/run` 是独立 tmpfs，不挂载宿主 systemd、D-Bus、Docker 或 Tailscale 控制套接字；镜像安装包期间保留 `policy-rc.d` 阻止服务启动。网络命名空间仍与宿主共用，以支持现有下载代理。写盘操作只针对脚本新建的 raw 文件及其 loop 设备，不接受宿主物理磁盘参数。这些限制不等同于完整虚拟机隔离，构建仍具有 root 权限并能访问绑定的 `/dev`、`/sys`；建议专用构建主机或虚拟机。

其他入口：

```bash
bash build.sh --help     # 无需 sudo，查看全部命令
bash build.sh test       # 安全测试、ShellCheck 和脚本语法检查
bash build.sh build --help
```

SSH 连接构建机器时，可使用 `tmux` 保持会话。终端显示主要步骤的开始、完成和耗时；长时间运行时每 30 秒显示当前步骤及已用时间。该提示说明步骤尚未结束，不代表下载一定有进展。详细工具输出保存在 `work/<build-id>/tools.log`，需要时在另一个终端查看：

```bash
sudo tail -n 50 -f /srv/ubuntu-customizer/work/<build-id>/tools.log
```

例如 debootstrap 会连续下载、解包和配置 Ubuntu 基础包；只要详细日志继续出现新的下载或配置记录，就应继续等待。构建未结束前不用重启构建命令。终端不会直接输出工具原始内容、完整命令参数或密码等输入。

默认要求工作与产物文件系统各自当前可用空间不少于 80 GiB、当前可用内存至少 4 GiB；如果两目录同盘，空间检查不代表预先保留两份 80 GiB。现有服务器适合开始验证，实际峰值以首次构建为准。

### 构建代理（可选）

构建期间的外部下载包括：

| 下载内容 | 来源 |
|---|---|
| uv 最新版本元数据 | `api.github.com`，固定版本时不查询此 API |
| uv 二进制和 SHA256 | `github.com/astral-sh/uv/releases` 及其重定向的 GitHub 资源域名 |
| Tailscale 密钥和软件包 | `pkgs.tailscale.com` 官方签名仓库 |
| v2rayA 最新稳定版本和 Debian 包 | GitHub API / Releases，包含代理核心和规则数据 |
| Ubuntu、Docker、Alpine | 默认阿里云国内镜像 |
| 构建宿主依赖 | 宿主现有的 APT 源 |

可在 `config/local.env` 添加以下配置；示例 IP 和端口需要换成构建机器能访问的 v2rayA HTTP 监听地址：

```bash
HTTP_PROXY='http://192.168.1.10:20171'
HTTPS_PROXY='http://192.168.1.10:20171'
NO_PROXY='localhost,127.0.0.1,::1,.aliyun.com,.tsinghua.edu.cn'
```

两个代理变量分别控制 HTTP / HTTPS 目标网址，应填写相同的 `http://` 代理地址；HTTPS 通过 CONNECT 隧道访问，仍验证目标站点证书。当前统一支持 HTTP 代理，不支持直接填写 `socks5://` / `socks5h://` 地址。v2rayA 端口以实际设置为准，不能直接填写 SOCKS 监听端口。

v2rayA 与构建脚本运行在同一台 Linux 主机时，可用 `127.0.0.1`；chroot 与宿主共用网络。代理在 Windows、另一台机器或容器里时，应使用构建机器可访问的地址；例如 VMware 客户机里的 `127.0.0.1` 指向客户机自身。跨机器访问需在 v2rayA 允许局域网连接，并放行对应监听端口。

代理地址建议直接填写可访问的 IP。宿主 `/etc/hosts` 中的自定义名称不会自动出现在构建 chroot 中；若报 `curl: (5) Could not resolve proxy`，把 `HTTP_PROXY` / `HTTPS_PROXY` URL 中的主机名换成代理实际 IP，端口保持原值。如果已有导出的同名环境变量，也要同步修改或取消导出，避免覆盖 `local.env`。

`NO_PROXY` 为逗号分隔的直连域名 / IP 列表，示例让国内镜像直连；清空它可让这些镜像也使用代理。使用主机名或域名后缀，不使用 CIDR 或通配符规则，以兼容各下载工具。

`setup` 与 `build` 都读取该文件。也可导出标准环境变量；入口会通过 sudo 保留这六个大小写代理变量。环境变量（包括显式空值）优先于文件，同一来源同时存在大小写时小写优先。禁用代理时将 `HTTP_PROXY` / `HTTPS_PROXY` 留空，并确认没有已导出的代理覆盖配置。

这里的代理地址和凭据仅传给构建进程、debootstrap、Ubuntu chroot 内的 APT / curl，以及 Alpine APK，不保存到镜像的 APT 配置、Shell 配置或 Docker 配置，也不配置 Docker registry 加速。它们与交付系统固定的本机 v2rayA / Docker 代理是两套独立配置。构建代理地址不进入公开构建报告；交付目录中的工具日志会对代理 URL 及其中的凭据脱敏。工作目录原始日志仍仅本机 root 可访问。

## 3. 公开构建配置

GitHub 下载故障可先运行 `bash build.sh check-downloads`（也接受 `--config /path/to/build.json`）。它使用与构建相同的 `.env` 和环境变量优先级，实际查询并下载校验 uv 与 v2rayA，在系统临时目录操作并自动清理，不需要初始密码、root 或构建依赖，不创建系统磁盘镜像或挂载，不发送 ntfy 通知。它会显示 HTTP / HTTPS 代理是否配置，以及 GitHub API、Release 和常见资源域名按 NO_PROXY 计算的路由；这些是本机配置结果，不能证明代理出口或远端节点正常。

下载和构建失败时显示 HTTP 状态码和失败域名，隐藏 URL 凭据、路径、签名查询参数、HTTP 原因文本和响应正文。403 可能来自 GitHub 限流、访问限制或代理策略，只有响应头明确表示额度为零才报告 API 限流；407 检查代理认证，404 检查 Release 资源或代理响应，429 等待后重试，502 / 503 / 504 检查代理及上游连接。uv 日志进一步区分 API 查询、校验文件下载和归档下载。

修改 `config/build.json`：

| 配置 | 默认值与作用 |
|---|---|
| `ubuntu_suite` | `noble`，首版仅支持 Ubuntu 24.04 |
| `ubuntu_mirror` | 阿里云 Ubuntu 源 |
| `docker_mirror` | 阿里云 Docker CE stable 源 |
| `python_index` | 清华 PyPI，生成 pip 与 uv 配置 |
| `alpine_release` | `latest-stable`；也可指定 `v3.xx` 分支 |
| `alpine_mirror` | 阿里云 Alpine 国内镜像：`https://mirrors.aliyun.com/alpine`，用于发布元数据、minirootfs 和 APK 仓库 |
| `alpine_fallback_mirrors` | APK 安装失败时依次尝试的备用源，默认清华 `https://mirrors.tuna.tsinghua.edu.cn/alpine`；设置 `[]` 可禁用切源 |
| `uv_version` | `latest`；也可指定精确稳定版本号，如 `0.x.y` |
| `template_gib` | 24，完整磁盘模板容量；目标盘需大于模板至少 1 MiB |
| `compression_threads` | 4，限制压缩及 squashfs 的并行度 |
| `work_dir` / `release_dir` | `/srv/ubuntu-customizer` 下的两个独立持久目录 |
| `cache_dir` | `/srv/ubuntu-customizer/cache`，持久缓存 APT `.deb`；设置 `null` 禁用，与工作目录、产物目录和仓库目录分离 |
| `minimum_build_free_gib` | 80，构建前磁盘空间检查阈值 |

基础软件清单为 `config/packages.txt`；Docker 和 Tailscale 在定制脚本中通过独立的签名仓库安装。Tailscale 使用官方 `https://pkgs.tailscale.com/stable/ubuntu`，与 Ubuntu / Docker 的国内镜像配置独立。Alpine 发布元数据和 minirootfs 使用配置的主镜像，APK 仓库优先使用同一镜像。每个 APK 镜像最多尝试 2 次，失败后等待 5 秒重试或切换下一备用镜像；默认主源阿里云、备用清华，最多共 4 次。每次用 `--no-cache` 重新获取索引，保持原分支的 main / community 仓库，不关闭签名验证；全部失败则中止构建。实际成功使用的 APK 源记录在构建报告的 `alpine.apk_mirror`。此回退仅针对 APK 安装，不涵盖发布元数据和 minirootfs 下载。构建需要能连接这些仓库和 GitHub Releases；安装目标机器时不需要下载软件。

### Ubuntu / Docker 下载缓存

构建默认使用 `cache_dir/apt/archives` 持久保存 `.deb`。debootstrap 通过 `--cache-dir` 复用基础包，Ubuntu chroot 中的 APT 将同一目录绑定到 `/var/cache/apt/archives`，以复用 Ubuntu / Docker / Tailscale 软件包。每次仍下载当前仓库索引、核验签名和包哈希，安装当前候选版本；版本变更或缓存未命中时照常联网下载，不以缓存固定旧版本。

日志会显示 `Persistent APT cache: N packages, X GiB`。这表示可用缓存量，实际下载 / 复用情况查看该次 `tools.log` 的 `Get:`、`Fetched` 和 APT 下载汇总。第一次构建仍需下载包；缓存不能加速包解压、配置、initramfs 生成或镜像压缩。构建期间 APT 保留下载包，对临时下载失败重试 3 次，HTTP / HTTPS 单次读超时为 30 秒；这些临时设置在交付镜像清理时移除。

清理镜像前先卸载缓存绑定，再执行 `apt-get clean`；卸载失败立即停止清理，避免删除持久缓存。缓存只包含包文件，不进入 ISO，也不会自动清空或淘汰；应为它保留磁盘空间。共享同一缓存的构建使用文件锁，避免同时改写；已有构建持锁时新构建直接停止。无需缓存时将 `cache_dir` 设置为 `null`。

如第一次从国内源下载也慢，先检查 `config/local.env` 的 `NO_PROXY` 是否包含 `.aliyun.com`、`.tsinghua.edu.cn`，避免国内下载绕行代理；具体速度仍取决于源站和本地网络。Ubuntu 和 Docker 镜像地址分别由 `ubuntu_mirror`、`docker_mirror` 控制。

不用 `ubuntu-server-minimal` 元包，因为它强制依赖 snapd。采用 `ubuntu-minimal`、`ubuntu-standard`，显式安装内核、固件、SSH、网络和确认的服务器工具，保留 Ubuntu Server 的 systemd、APT、sudo 与 root 锁定方式。

构建还会预置常用维护配置：journald 持久日志上限 500 MiB（保留 1 GiB 空间，运行时日志上限 128 MiB，最多保留 30 天）、`ntp.aliyun.com` / `ntp.tencent.com` 时间同步、每周 `fstrim.timer`、SSH 每 60 秒保活探测、tmux 鼠标和 50000 行历史记录，以及禁用 core dump 持久化。`server-info` 只读汇总主机、网络、磁盘、服务、Docker、Tailscale 和重启状态；`server-update` 由用户手动执行，刷新索引并运行带正常确认的 `apt-get upgrade`，不会自动重启或 `autoremove`。

tmux 默认配置在镜像构建时写入 `/etc/tmux.conf`，安装后新建会话即可使用鼠标滚轮查看历史输出，无需手动开启。构建验收以 `ubuntu` 用户正常启动独立的 tmux 服务，不使用 `-f` 强制加载，并检查鼠标为 `on`、历史为 50000 行、窗口编号从 1 开始。已有 tmux 服务不会自动重读配置，可执行 `tmux source-file /etc/tmux.conf`；个人 `~/.tmux.conf` 或 `~/.config/tmux/tmux.conf` 仍可覆盖系统默认值。旧 ISO 安装的系统不会因更新项目源码而自动获得这些配置。

### 交互提示显示

Alpine Live 启动完成、进入安装器后先展示青色 ASCII Logo 和英文欢迎页，说明 Ubuntu Server 24.04 LTS x86_64、离线整盘安装及数据覆盖风险。第 1/3 步等待输入 `y` / `Y` 回车才开始读取镜像清单、校验镜像和发现磁盘；没有超时，不启动选盘倒计时，其他输入、直接回车或输入结束均停止安装。构建阶段的 `--check-tools` 不进入交互。Linux 内核和 Alpine 启动日志仍可能在欢迎页之前显示。

安装器将需要操作的步骤与日志分开显示，使用空行、分隔框、`ACTION REQUIRED` 步骤编号及 `>>>` 输入标记。第 2/3 步选盘为黄色提示，默认等待 30 秒；任何按键停止自动选择倒计时。第 3/3 步清盘为红色提示，重新列出目标磁盘路径、型号、序列号和容量，明确显示正在等待输入、没有确认超时；只有输入 `y` / `Y` 后回车才允许继续。欢迎页确认只授权开始检查，选盘超时仍只选择默认盘，二者都不授权写盘。

提示不清屏，前面的日志仍可回看。仅在支持颜色的交互输出终端中使用 ANSI 颜色；输出重定向、`TERM=dumb` 或设置了 `NO_COLOR` 时保留纯文本框和操作说明。`server-update` 在刷新索引后、调用 `apt-get upgrade` 前也显示独立提示框，提醒查看 APT 的软件包汇总并在其原生提示处确认，不增加一次额外确认。

安装成功后显示独立绿色完成框，列出目标磁盘、构建编号和后续操作：拔出安装 U 盘或断开虚拟机 ISO，在 Live Shell 执行 `reboot`，进入安装后的 Ubuntu 用 `ubuntu` 和镜像预设密码登录，然后执行 `passwd` 修改密码，需要 Tailscale 时执行 `sudo tailscale up` 并按链接认证。明确提示改密和认证操作应在重启进入 Ubuntu 后执行；不显示密码明文，也不自动重启。失败时保留单独的恢复 Shell 提示，不显示成功框。

### Docker 使用权限

`ubuntu` 不加入 `docker` 组，管理系统级 Docker 守护进程时通过 sudo 授权。Docker 守护进程以 root 运行，能访问其 socket 的用户可以创建挂载宿主根目录的容器并修改宿主系统，因此加入该组相当于授予无需 sudo 验证的 root 控制能力。构建验收确认 `ubuntu` 不属于该组，且 sudo 策略仍要求密码；Docker CLI、Buildx、Compose 的版本命令以普通用户执行，不需要访问守护进程。构建阶段不启动 Docker 守护进程。

安装后以 `ubuntu` 登录，执行以下命令验收：

```bash
id -nG
sudo docker ps
docker compose version
```

可另行执行 `sudo docker run --rm hello-world` 验证镜像拉取和容器启动，此步骤需要访问容器镜像仓库。若现有机器曾把 `ubuntu` 加入 `docker` 组，可执行 `sudo gpasswd -d ubuntu docker` 后重启，使已有登录和 tmux 会话中的旧组权限一并失效。已生成的 ISO 不会因源码变更自动更新，需要重新构建。

### v2rayA 与 Docker 代理

每次构建通过官方 GitHub API 解析 v2rayA 最新非预发布版本，下载官方 amd64 Debian 包并核对 Release 资产的 SHA256；没有预期安装包或摘要时中止构建，不跳过校验。当前官方安装包包含 Web 界面、`v2raya_core` 和 geoip / geosite 数据，无需安装后再下载核心。实际包版本、下载地址、摘要与核心版本写入构建 manifest 的 `v2raya` 项；已安装包版本和 `/var/lib/ubuntu-customizer/v2raya-release.json` 也留在系统中。未来最新版本若改变包结构、API 或配置存储而不兼容，构建检查会报错，需要适配后重建，不静默生成缺少组件的 ISO。

| 项目 | 镜像预置 |
|---|---|
| 服务 | 原生 `v2raya.service` 开机自启，不通过 Docker 运行 |
| Web 界面 | `0.0.0.0:2017`，UFW 放行 TCP 2017，浏览器直接访问服务器 IPv4 地址 |
| 本机代理 | SOCKS5 `127.0.0.1:20170`、HTTP `127.0.0.1:20171`、规则 HTTP `127.0.0.1:20172`；关闭局域网代理共享，不放行这些端口 |
| 代理方式 | lite 模式，关闭透明代理与 DNS 模块 / 接管，保留系统的 systemd-resolved；不配置系统全局代理 |
| IP 转发 | v2rayA 配置为开启，匹配 Docker 需要，避免连接节点时把 Docker 已开启的转发关闭；UFW 普通转发默认仍拒绝 |
| Docker | `/etc/docker/daemon.json` 的 `proxies.http-proxy` 和 `https-proxy` 都为 `http://127.0.0.1:20171`，沿用日志轮转，不写 `registry-mirrors` |
| 直连范围 | Docker 的 `no-proxy` 排除 localhost、回环、RFC1918 私有 IP 段和 `.local` / `.localhost` 域名；内网仓库使用其他域名时需自行补充域名 |
| 账号与节点 | 不预设 Web 管理账号、节点或订阅；第一次访问创建独立的管理账号，和 Ubuntu 登录账号分开 |

安装后打开 `http://服务器IP:2017`，创建管理账号，导入节点或订阅，选择节点并点击连接 / 启动。单纯导入节点不会自动连接。默认 HTTP 端口 20171 走所选代理节点，Docker 已提前配置这个端口；节点启动后重试拉取即可，无需修改 Docker 配置或重启 Docker。以后正常关机重启会沿用本机的节点配置和 v2rayA 保存的运行状态；手动停止核心或节点失效时代理不可用。

```bash
systemctl is-active v2raya docker
sudo ss -lntp | rg ':(2017|20170|20171|20172)\b'
# 完成 Web 节点连接后：
curl --proxy http://127.0.0.1:20171 -I https://registry-1.docker.io/v2/
# registry 返回 HTTP 401 通常表示网络已通，未携带仓库认证属于正常情况。
sudo docker pull hello-world
sudo docker run --rm hello-world
```

没有节点、节点未连接或 v2rayA 故障时，Docker 外网拉取将报连接失败，不自动退回直连；Docker 服务、已存在的本地镜像和容器运行不以节点就绪为启动条件。`Wants` / `After` 仅安排 v2rayA 服务启动顺序，不等候人工导入节点，不增加 Docker 启动阻塞。普通 `docker build` 使用的守护进程镜像拉取可使用此代理，但容器应用、Dockerfile 的 `RUN` 命令和独立的 `docker-container` BuildKit 实例不会自动获得代理，需要按需单独配置；不向 `~/.docker/config.json` 注入代理，也不把宿主 `127.0.0.1` 传给容器。终端 curl / APT 等仍按原配置直连，可单次使用 `curl --proxy`。

构建验收在额外的私有网络命名空间中启动无节点的 v2rayA，通过官方 API 写入端口、非透明模式、DNS 关闭和转发预置，并检查内置 Web 页面。临时随机账号只用于构建，停止实例后通过官方 `--reset-password` 清除，再以只读方式确认持久配置存在且账号、节点、订阅表为空。构建不会调用节点导入或连接接口，不在宿主网络中启动 v2rayA，不改变宿主 Docker 的配置。预置在打包前完成，首次开机不运行初始化脚本；实际代理转发和 Docker 拉取需安装后由用户连接自己的节点验收。

Web 端口按已选方案对可达网络开放，首次登录请及时创建管理账号。后续仅允许指定管理网络访问时，可先删除通用规则，再按实际网段放行，例如 `sudo ufw delete allow 2017/tcp`、`sudo ufw allow from 10.1.1.0/24 to any port 2017 proto tcp`。这里为 HTTP 管理入口，应在可信网络或 Tailscale 中访问。v2rayA 以独立 `.deb` 安装，未接入第三方 APT 源；`server-update` 不会自动获取其 GitHub 新版本，后续通过重新构建 ISO 或手动核验安装新版本维护。

临时恢复 Docker 直连时，在 `/etc/docker/daemon.json` 删除整个 `proxies` 对象，保留其他配置并确保 JSON 有效，执行 `sudo dockerd --validate --config-file=/etc/docker/daemon.json` 后 `sudo systemctl restart docker`；此操作会重启 Docker 服务。不要为了恢复直连删除整个日志配置文件。

### 终端代理快捷命令与检查

安装后的 Bash 登录终端、普通交互终端和新建 tmux 窗口提供以下命令。打开新会话仅加载函数，不自动启用代理；从已启用代理的父进程启动子终端时，仍会继承其环境变量。

```bash
proxy-on       # 当前终端启用本机 HTTP 代理，先在 v2rayA 连接节点
proxy-status   # 查看大小写代理变量；自定义地址隐藏，避免显示账号密码
curl -I https://github.com/
proxy-off      # 清除当前终端的代理环境变量
proxy-check    # 无需 sudo，检查服务、端口、GitHub HTTPS 和 Docker Registry
```

`proxy-on` 同时导出大小写 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 及 NO_PROXY，使用 `http://127.0.0.1:20171`。回环、常见私有 IP 段、`.local` / `.localhost`、阿里云和清华镜像域名加入绕过列表；不同程序对 NO_PROXY / CIDR 的支持不同，内网自定义域名需按需补充。`proxy-off` 清除这些变量，不恢复启用前的自定义代理。开关不修改系统文件或 Docker 配置，已运行进程不受影响；sudo 通常不保留代理变量，非 Bash Shell 需自行配置。不建议为代理修改 sudo 全局环境保留策略。

`proxy-check` 不导入节点、不调用 Docker 拉取、不修改配置或重启服务。每项请求均显式使用本机代理、忽略当前终端代理环境和用户 curl 配置，保留 TLS 证书校验，设置连接与总超时。代理端口未监听时跳过外网检查并提示连接节点；Registry 的 HTTP 401 视为可达，其他失败显示 HTTP 状态和 curl 退出码。全部通过返回 0，否则返回 1。该命令验证服务和代理网络连通，不代表 Docker 配置正确或实际镜像拉取已经成功，最终仍用 `sudo docker pull hello-world` 验收。

当前正在使用的旧系统不会自动获得新命令，需要重建 ISO；手动加载已安装的 Bash 函数可执行 `source /etc/profile.d/customizer-proxy.sh`。构建验收只运行本地开关检查和 `proxy-check --help`，不会借用构建机节点进行外网代理测试。

### ntfy 内网 IP 通知

在构建机的 `config/local.env` 添加三项，或填写示例文件已有的空值：

```bash
NTFY_URL='https://ntfy.example.com'
NTFY_TOPIC='server-status'
NTFY_TOKEN='tk_your_token'
```

`NTFY_URL` 是 ntfy 服务的根地址，不包含 Topic（有反向代理路径前缀时保留前缀，不包含查询参数或 URL 账号密码）；Topic 使用 1-64 位英文字母、数字、下划线或短横线。Token 使用实际 ASCII Token。三项必须全部填写或全部留空，部分填写会在开始构建前报错。环境变量优先，包括显式空值；入口 sudo 会保留这三个变量。HTTP 地址也可配置，但 Bearer Token 会以明文传输，建议使用证书有效的 HTTPS 地址。服务会拒绝 HTTP 重定向，应填写最终服务地址。

构建将配置直接写入镜像内 `/etc/ubuntu-customizer/ntfy.json`，目录权限 0700、文件权限 0600，均属于 root；Token 不通过外部命令参数或公开构建报告传递，发布日志中的 URL、Topic、Token 会脱敏。Token 不会加密，生成的 ISO 和工作目录中的 raw 镜像均包含它，需私人保存；建议使用仅有目标 Topic 发布权限的 Token。构建不会发送通知，只检查格式、文件权限和定时器启用状态，不能据此确认服务端权限或消息送达。

配置后预先启用 `ubuntu-ip-notify.timer`，开机约 30 秒开始检查，每次运行结束约 30 秒后再检查。DHCP 没有地址时继续等待；每次开机第一次取得地址后发送上线通知，同一次开机仅在主机名或地址集合变化时再次发送。通知包含主机名、各网卡的 RFC1918 内网 IPv4 和 `ssh ubuntu@地址`。通过 `/sys/class/net/*/device` 筛选实际网卡（含常见虚拟机网卡），排除回环、网桥、veth、Tailscale 等虚拟接口；bond / VLAN 上的地址及公网 IPv4、IPv6 不在本版采集范围。

消息通过原生 ntfy JSON 发布接口发送，使用 `Authorization: Bearer ...`，不依赖 Docker 或 v2rayA，也不继承终端/构建代理。单次 HTTP 请求超时 15 秒，服务总超时 25 秒；网络不可达、认证失败等均在后续定时检查重试，不阻塞开机或 SSH，不修改网络、DNS 或防火墙。若 ntfy 只能通过 Tailscale 到达，会在该网络可用后重试。成功状态保存在 `/run/ubuntu-ip-notify/sent.json`，只在服务端确认后更新，重启自动清空。正常成功后地址不变不会每 30 秒重复发消息；发送已到达但本机未收到确认时，重试可能产生重复通知。

安装后验收：

```bash
sudo ntfy-ip-notify --check-config                 # 只校验，不发送、不显示 Token
systemctl is-enabled ubuntu-ip-notify.timer
systemctl list-timers --all ubuntu-ip-notify.timer
sudo systemctl start ubuntu-ip-notify.service      # 立即检查；符合发送条件才发送
sudo journalctl -u ubuntu-ip-notify.service -n 30 --no-pager
```

失败日志仅显示异常类型或 HTTP 状态，401 / 403 可检查 Token 与 Topic 发布权限；不会输出响应正文或 Token。安装后如需修改配置，使用 `sudoedit /etc/ubuntu-customizer/ntfy.json`，下次检查自动读取。强制重新通知可执行 `sudo rm -f /run/ubuntu-ip-notify/sent.json`，再启动 service；停止后续通知可执行 `sudo systemctl disable --now ubuntu-ip-notify.timer`。三项留空的 ISO 不创建凭据文件，也不启用定时器；以后手动添加配置时仍需设置目录 0700 / 文件 0600，再执行 `sudo systemctl enable --now ubuntu-ip-notify.timer`。

这是每次开机持续运行的通知服务，所有程序和配置在构建阶段已安装，不执行首次开机安装或系统初始化。当前仅实现 ntfy 通知，控制台登录页保持原有配置。

### UFW 防火墙预置

镜像预装并启用 UFW，使用 Ubuntu 提供的默认 before / after 规则保留回环、已建立连接和必要的 ICMP / IPv6、DHCP 处理，统一管理 IPv4 / IPv6：

| 范围 | 默认策略 |
|---|---|
| 宿主入站 | 拒绝，显式放行 TCP 22（SSH）和 TCP 2017（v2rayA Web） |
| 出站 | 允许，APT、DNS、NTP、Tailscale 等可正常访问网络 |
| 普通转发流量 | 拒绝；Docker、Tailscale 仍可添加各自需要的规则 |
| 独立 nftables 服务 | 保持禁用，保留 `nft` / `iptables` 诊断工具 |

构建时先用 debconf 保持新安装的 UFW 未启用；在额外的 `unshare --net` 私有网络命名空间中配置默认策略、加入 SSH 和 v2rayA Web 放行规则、启用并验证防火墙。共享镜像文件系统中的持久配置得以保留，临时网络规则随命名空间退出销毁，不修改构建宿主的防火墙。此操作失败会中止构建，不能回退到宿主网络继续运行。镜像中启用标准 `ufw.service`，系统正常启动即加载预置规则，无需首次开机初始化脚本。构建验收核对开机启用状态、IPv4 / IPv6 SSH 与 Web 规则和默认策略，不在宿主共用的网络中执行 `ufw enable` / `reload`。

安装后可执行：

```bash
sudo ufw status verbose
sudo ufw status numbered
sudo ufw allow 443/tcp
sudo ufw delete allow 443/tcp
```

SSH 端口发生变化时，先放行新端口并从另一连接确认可登录，再删除旧端口规则；需要在本地控制台恢复访问时可执行 `sudo ufw disable`，修复规则后再启用。Tailscale 认证仍由用户执行 `sudo tailscale up`，客户端通过自己的 netfilter 规则处理隧道流量，基础镜像不开放额外业务端口；如需改善 UDP 直连，可按实际 tailscaled 监听端口放行，例如 `sudo ufw allow 41641/udp`。

**Docker 发布端口可能绕过 UFW 普通入站规则。** 不设置 Docker 的 `iptables=false`，不清空 Docker 的转发 / NAT 链。只供本机访问的服务应显式绑定回环，例如 `-p 127.0.0.1:8080:80`；需要公网或局域网访问控制的容器，应按业务通过当前 Docker iptables 后端的 `DOCKER-USER` 链限制来源。基础镜像不预置未知业务的容器端口规则。

首次安装验收应在本地或虚拟机控制台保留恢复入口，并从另一机器确认 SSH 22 可达、未放行的宿主测试端口被阻挡、DHCP / DNS / HTTPS / 时间同步正常、Tailscale 认证后可用；另行确认 Docker 容器的联网与端口发布行为。`sudo server-info` 会显示实时 UFW 状态。修改 UFW 规则或执行 reload 后也应复查 Docker / Tailscale 的连通性。

Alpine 根文件系统按官方发布元数据的 SHA256 校验，APK 使用默认签名验证；uv 预编译包按对应发布的 SHA256 校验。每次构建记录实际解析版本及源码文件摘要。APT / APK 仓库持续更新，因此这还不是逐字节可重现构建；要完全复现需额外保存仓库快照。

## 4. 接入 GitHub 自托管 Runner（暂缓）

以下内容保留供后续接入，当前本地命令行构建不需要执行本节。

1. 仓库 **Settings → Actions → Runners → New self-hosted runner**，选择 Linux x64。
2. 在现有服务器使用独立目录，按 GitHub 页面给出的命令安装和注册 Runner；添加标签 **`ubuntu-customizer`**。注册 Token 使用页面临时值，不写入仓库。
3. 将 Runner 安装为系统服务，确保能出站连接 GitHub；不需要为 workflow 开放公网 SSH。
4. 为仓库添加 Actions Secret **`UBUNTU_INITIAL_PASSWORD`**，填写约定的密码。Actions checkout 会清理工作区，不要依赖该工作区里的私有 `local.env` 长期保留。
5. Runner 服务用户需要免交互运行构建入口的 sudo 权限。此任务会执行 root 脚本，因此 Runner 只供你信任的仓库和默认分支使用，不接收外部 PR 脚本。

例如 Runner 用户是 `actions-runner`，用 `sudo visudo -f /etc/sudoers.d/ubuntu-customizer` 按实际账号设置：

```sudoers
Defaults:actions-runner env_keep += "UBUNTU_INITIAL_PASSWORD"
actions-runner ALL=(root) NOPASSWD: /usr/bin/bash
```

这是构建专用账号的权限配置。交付系统中的 `ubuntu` 用户仍要求正常输入 sudo 密码。不要把 Runner 用户改成目标系统的预设账号，也无需调整宿主 Docker、Snap 或软件源。

入口内部通过文件锁串行执行，workflow 也设置全局 concurrency 且不取消正在执行的构建。任务最长 360 分钟；正常中断会尝试卸载临时挂载并释放 loop，强制终止后需检查残留 loop 后再清理目录。

### 4.1 现有 Docker Compose Runner 的适用情况

已读取现有 `core-node-deploy/apps/github-runner/compose.yaml`，并仅核对其 `.env` 中的非机密资源与标签配置：

| 项目 | 当前配置 | 与本项目的关系 |
|---|---|---|
| Runner 服务 | 3 个，镜像为 `myoung34/github-runner:latest` | 是共享 Runner 部署，尚未作为本项目专用构建环境验证 |
| 容器特权与设备 | 未配置 `privileged`、额外 capabilities 或设备映射 | 当前构建需要的 `unshare`、mount 和 loop 操作无法直接在默认 Docker 权限下运行；容器里 sudo 不能补足 Docker 限制的权限 |
| 运行账号 | `RUN_AS_ROOT=false` | 还需核对容器内构建依赖和 sudo 配置 |
| 每个 Runner 的资源 | 4 CPU、8 GiB 内存 | 来自当前私有配置中的非机密字段；3 个任务并发时需合计资源占用 |
| Runner 标签 | `self-hosted,linux,core-node` | 不包含 workflow 要求的 `ubuntu-customizer`，当前完整构建任务会等待匹配的 Runner |
| 数据卷 | 工作目录、注册状态和宿主 Docker socket | 没有映射 `/srv/ubuntu-customizer`，仅在容器内生成 ISO 无法满足服务器持久保存约定 |
| Docker socket | 挂载宿主 `/var/run/docker.sock` | 可以控制宿主 Docker；这不等同于当前容器有 mount 权限，也不能视为与宿主完全隔离 |

结论：现有 Compose 不能直接运行当前完整构建脚本。仅加标签或安装依赖不会解决设备权限与产物持久化问题。

对于继续承载其他业务的服务器，推荐另设一台专用 Ubuntu 构建虚拟机，在其中注册带 `ubuntu-customizer` 标签的 Runner；现有三个容器继续承接原有任务。构建虚拟机只使用虚拟磁盘，不直通宿主物理盘，产物持久保存在该虚拟机磁盘中，再通过 SFTP / SCP 获取。这样宿主不需要安装本项目的构建工具。

如果改为 Docker 内直接执行当前脚本，需要另行设计可用的 mount / loop 设备权限和宿主产物映射。直接添加 `privileged: true` 或挂载整个宿主 `/dev` 会扩大对宿主设备的访问能力，不能据此承诺宿主安全。目前未修改外部 Compose、未创建容器、也未给已有 Runner 增加权限。

上述判断依据本地部署文件；实际服务器若使用了额外 Compose override 或不同镜像，应以实际运行容器的配置为准。

## 5. 获取产物与可选的 workflow

当前本地构建成功后，直接进入终端提示的 `/srv/ubuntu-customizer/releases/<build-id>/` 获取 ISO，执行 `sha256sum -c SHA256SUMS` 校验。Windows 可通过 SFTP / SCP 下载；不需要打开 GitHub Actions，脚本也不会上传任何文件。

以下为将来恢复 workflow 时的操作：

代码推送到仓库默认分支后：

1. 打开 **Actions → Build Ubuntu installer → Run workflow**，选择默认分支。
2. `checks` 在 GitHub 托管环境运行，成功后 `build` 等待上述自托管 Runner。
3. 本地产物目录的 build-id 是 `gha-<run_id>-<run_attempt>`。

完整 ISO 不进入 Artifact、Release、Cache 或其他 GitHub 存储。Artifact 仅显式上传仓库 `reports/` 下这五个文件，保留 14 天：

```text
build-report.json
build.log
manifest.json
packages.txt
SHA256SUMS
```

原始日志、私有配置、ISO 和磁盘文件不进入该目录。上传失败也不会删除服务器上的 ISO。下载时使用 SFTP，或在自己的电脑执行：

```bash
scp <server-user>@<server>:/srv/ubuntu-customizer/releases/<build-id>/ubuntu-custom-server.iso .
scp <server-user>@<server>:/srv/ubuntu-customizer/releases/<build-id>/SHA256SUMS .
sha256sum -c SHA256SUMS
```

Windows 可用 `Get-FileHash .\ubuntu-custom-server.iso -Algorithm SHA256` 与 `SHA256SUMS` 对比。

## 6. 安装和验收

- 关闭 Secure Boot；虚拟机挂载 ISO，实体机使用 DD 模式写入 U 盘，不使用 Ventoy。
- Alpine 根系统载入内存，压缩 Ubuntu 磁盘留在安装介质。Live 的第二终端（Ctrl+Alt+F2）提供本地恢复 Shell。
- 构建时在 Alpine chroot 内检查安装与收尾所需工具，全部通过才打包 ISO；Live 安装器在读取介质和选择硬盘前再次检查。Alpine 的 `sgdisk` 需安装独立软件包，`gptfdisk` 不包含该命令。
- 校验压缩镜像后显示候选盘。倒计时 30 秒，无操作选最大盘；任意选择输入取消倒计时，随后可以继续手动输入编号。
- 排除安装盘、USB / 可移动盘、只读盘、容量不足、非 512 字节逻辑扇区、已挂载或有 swap / 活动映射占用的盘。识别不出安装介质时停止。
- 最终确认输入 **`y`** 后回车（也接受大写 `Y`），没有超时。直接回车或其他输入取消，不写盘。这个倒计时不会自动确认清盘。
- 确认并再次核对目标盘后，先清理该盘原有分区及整盘的文件系统 / RAID 签名，再写入母镜像；否则大硬盘尾部的旧 ZFS 等签名可能存活，引发 UUID 探测冲突。清理仅使用已核对设备 FD，先清分区再清分区表；失败立即停止，不能继续写镜像或报告成功。此操作不是全盘安全擦除，不保证旧数据不可恢复。
- 安装器解压写入、检查全部流和字节数，刷新并失效块缓存后回读 raw 覆盖区，核对 SHA256，再修复 GPT、扩容 ext4、重建磁盘标识、machine-id、SSH 密钥和双模式引导。
- 收尾从内核 sysfs 的 `partition` 属性识别根分区 3 / EFI 分区 2，核对父盘及设备主次编号，并最多等待 10 秒让设备节点就绪；不依赖 Alpine Live 中可能为空的 `lsblk PARTN` / udev 属性。
- 修改 ext4 / FAT 标识后通过 `blkid -p` 直接读取并校验 UUID，再写入 fstab，避免使用旧缓存；构建母镜像时也等待根分区和 EFI 分区节点均就绪后才格式化。Live 显式加载 Intel VMD 和常见 MMC 控制器模块，补充实体机存储识别。
- 安装成功后手动拔盘并重启；使用预设账号登录，自行 `passwd` 修改密码、`sudo tailscale up` 认证。
- 安装收尾使用目标 Ubuntu 的 `blkid -p` 验证根分区 / EFI 分区能唯一识别，且文件系统类型、UUID 与配置一致；仅在 Alpine 中成功挂载不能替代此检查。存在签名冲突时停止并报告安装未完成。

静态检查不表示硬件兼容性已经通过。首次 Linux 构建完成后，请按主方案第 14 节测试 BIOS / UEFI 启动、虚拟机安装、多磁盘排除、断网安装、实体 U 盘安装、SSH、Docker 实际运行和 Tailscale 认证。构建报告明确将启动测试和安装测试记为 `not_run`，人工验收为 `pending`。

## 7. 排错

命令行终端显示阶段摘要，详细工具输出见 `work/<build-id>/tools.log`；构建有进展时还会保存脱敏副本到 `releases/<build-id>/logs/tools.log`。子命令失败时，终端显示命令名称、退出码和具体日志路径；镜像内验收失败时，详细日志还会显示失败检查的 Shell 行号和命令。由于代理导出语句也通过标准输入传入，该行号包含这些前置语句。失败时不把部分 ISO 发布为最终文件名。没有 `.git` 时 manifest 的 `git_commit` 为 null，仍记录构建输入文件的 SHA256。

| 现象 | 检查内容 |
|---|---|
| `build` 一直排队 | Runner 是否在线、是否同时具有 self-hosted / linux / x64 / ubuntu-customizer 标签 |
| sudo 要求密码或拒绝保留环境变量 | Runner 服务账号的 sudoers 及 Secret 环境变量配置 |
| preflight 拒绝 | 初始密码、依赖、资源、build-id 是否重复、两个 GRUB 平台模块是否安装 |
| APT / APK / uv 下载失败 | 对应站点的 DNS / HTTPS 访问；不会静默更换 Ubuntu / Docker 镜像源 |
| Live 启动找不到介质 | 是否直接写入混合 ISO、介质标签和文件是否完整；Ventoy 不在支持范围 |
| 收尾提示 `sgdisk: command not found` | 旧 ISO 漏装了 Alpine 独立的 `sgdisk` 包；更新构建脚本、重新构建 ISO 后重新安装，当前这次收尾未完成 |
| 没有候选盘 | 磁盘是否为内置盘、容量 / 扇区是否匹配、是否存在挂载 / swap / 映射占用 |
| 收尾在 `Locating root and EFI partition devices` 停止，EFI 路径为空但 p2 存在 | 旧版通过 `lsblk PARTN` 查找分区，Alpine/mdev 环境可能没有该属性；更新后重新构建 ISO，改用内核 sysfs 编号识别并核对设备节点 |
| 安装后 `UUID does not exist`，但手动 ext4 挂载成功 | 用 `LIBBLKID_DEBUG=all blkid -p <根分区>` 检查双签名，`blkid -p -n noext4 -o export <根分区>` 识别第二类型；已发现旧 `zfs_member` / `boot-pool` 尾部签名与新 ext4 冲突。不要直接无类型限制地 `wipefs -a` |

旧 ISO 安装后如已确认上述 ZFS 冲突，可从 U 盘进入 Live，停留欢迎页并切到第二终端（Ctrl+Alt+F2），先用 `lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS` 确认设备，再用 `findmnt --source /dev/nvme0n1p3` 确认根分区未挂载。仅针对已确认的目标根分区执行 `wipefs --all --types zfs_member --backup /dev/nvme0n1p3`，随后 `blkid -p /dev/nvme0n1p3` 应唯一识别为 ext4、UUID 与启动配置一致，再 `sync` 并拔盘重启。设备路径按实际检查结果替换；这里必须保留 `--types zfs_member`，不能无过滤擦除新 ext4。签名备份在 Live 的 root 家目录，位于内存，需留存时应在重启前另存。

### 安装异常报告

Live 安装器会同时显示并记录 Python、外部工具和安装收尾脚本的输出。发生异常时，屏幕最后显示 `[ERROR] INSTALLATION STOPPED` 报告，包含失败阶段、目标盘、build-id、是否已开始修改目标盘、异常类型、失败命令 / 退出码，以及最近的日志。收尾脚本还提供 Shell 行号；显式退出、分区设备缺失和文件系统检查失败也会记录原因。

每次运行使用独立目录 `/var/log/ubuntu-customizer/install-<UTC时间>-<随机后缀>/`：

- `installation.log`：完整安装输出、Python traceback 和自动采集的只读诊断。
- `error.txt`：屏幕错误摘要，便于复制或拍照。
- `finalize-stage.txt` / `finalize-error.txt`：收尾阶段及命令错误记录（进入相应阶段才会产生）。

诊断自动收集磁盘 / 分区信息、目标盘分区表、挂载状态、内核日志，以及目标盘前 8 个分区的文件系统 / 签名探测；每条命令设有超时。诊断不会清盘、修复文件系统、重新写入、重启或上传报告。可在恢复终端使用 `less <报告目录>/installation.log` 查看详情；日志可能包含主机和磁盘标识。

**这些日志位于 Live 内存，重启会丢失。** 如需保留，请在重启前将整个报告目录复制到另一个已挂载的可写介质。安装器不会为了存日志而自动挂载或写入目标盘；没有出现安装完成提示时，按安装未完成处理。此报告覆盖 Live 安装器开始运行后的异常，固件 / GRUB / Live 内核启动前的错误仍需查看启动画面。

失败构建不会继续写盘或标记为安装成功。查看本地日志后修复原因，用新的 build-id 重试。
